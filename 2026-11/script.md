# ブラウザのコンソールに貼るだけ　台本

2026年11月14日 CraftStage LT会（AIなんでもLightning Talk交流会）／富士通UIS（川崎）の台本です。スライドは[こちら](https://yaenowa-yoshida.github.io/ailt-presentations/2026-11/)です。

話す本文は約2,570字で、1分あたり約310字として約8分20秒です。

## 1. タイトル（0:00〜0:10）

Claude Code と、2つのサイトの受け入れテストを回した話です。スクリプトを書くのはAI、ブラウザに貼って流すのは私です。

## 2. 自己紹介（0:10〜0:25）

株式会社ヤエノワの吉田です。ECと基幹システムの連携設計や、要件定義をしています。B2B発注システムやシミュレーターシステムの受け入れテストも担当しています。

## 3. AIを使わないサービス（0:25〜1:00）

まず、テストを作って動かす有料のサービスを紹介します。AIを使わないものでは、テスト代行があります。テスト項目づくりから実行、不具合の報告までを、テストの会社の人が受け持ちます。テスト自動化ツールは、人が画面の操作を記録して、ツールが何度でも流します。参考までに、テスト代行は1日あたり約3万〜18万円、ツールは月5千円くらいからです。

## 4. AIを使うサービス（1:00〜1:25）

AIを使うものも増えています。仕様書からテストケースを作るもの、文章の指示でテストを作って流すもの、画面が変わったときにテストを自動で直すものがあります。設計書から合否判定、不具合の記録まで受け持つサービスも出てきています。料金は、月2千円くらいから9万円くらいまでです。

## 5. 2つの案件（1:25〜2:10）

私がやったのは、2つの受け入れテストです。1つめは、受発注システムの改修で、81ケースです。見られるのは画面だけで、node もヘッドレスの Chrome も使えません。発注すると、テスト環境に受注ができて在庫も減ります。

2つめは、ユニフォームのカスタム注文サイトの新商品で、70品番あまりです。テストの項目は1品番あたり約270手順あります。デザインから注文書、受付と確定、工場向けのデータまでを、全品番で通して確かめる仕事です。

どちらも、サイトを開いているのは私のブラウザです。

## 6. 仕組み（2:10〜2:35）

そこで、Claude Code がスクリプトを書き、私が貼って流します。その結果を Claude Code が読んで判定し、記録します。1つめの案件では、判定をOK、NG、要確認、保留の4つに分けました。結果は文字で残すので、AIの判定を人があとから確かめられます。

## 7. 手順（2:35〜3:30）

手順はこうです。まず、AIで仕様書をつくります。テストシナリオは、基本的に自分でプロンプトに打ち込んで作りました。次に、商品とそれに付随するデータをダウンロードして、テストデータもAIで作ります。そのうえで、シナリオに合わせて Claude Code がスクリプトを書きます。それを私がブラウザで実行すると、Claude Code が結果を検証して、チェックシートにOKとNG、指摘点を記入します。人がやるのは、シナリオを打ち込むことと、ブラウザで流すことです。1つめの案件では、1本のスクリプトをコピーして、別の確認用に作り替えていきました。

## 8. エージェントの紹介（3:30〜4:10）

1つめの案件で働いてくれた、4つのエージェントを紹介します。実行計画係は、次にどのスクリプトを、どの得意先と設定で流すかを決めて、進み具合も教えてくれます。読むだけで、何も書き換えません。スクリプト作成係は、決まりを守ってスクリプトを書きますが、流しはしません。結果記録係は、結果を判定してシートに記録します。ただし書き込むのは、私が「書き込んでよい」と言ったときだけです。仕様調査係は、仕様書や経緯の記録を調べて、根拠つきで返してくれます。

## 9. 止まる仕組み（4:10〜4:50）

工夫の一つは、想定と違えば止まることです。1つめの案件では、開始前にカートが空かを確かめ、アカウントや得意先が違えば発注しません。発注した注文は、直後に画面からキャンセルします。こうした作りは、画面のスリープを止めるといったものと合わせて、7つの型にまとめました。2つめの案件では、金額をその場で計算して違えば止まり、注文番号がずれたら押さずに止まります。流し終えた注文は「済み」と記録して、二度流さないようにしました。

## 10. 残す仕組み（4:50〜5:20）

もう一つは、決めたことを次の会話に残すことです。1つめの案件では、作業のルールを CLAUDE.md に書き、決めたことや訂正はメモリに残して、約35件になりました。2つめの案件では、OKにした根拠を備考に書き、途中から伝えた「いちいち確認しなくていい」も、メモリに残しました。

## 11. 成果（5:20〜6:00）

どちらの案件でも、回帰テストと、決まった内容を再現する作業の時間が、圧倒的に短くなりました。2つめの案件では、手作業だと1件10分以上かかる注文が約30秒になり、33件を通して回しました。工場向けの送付パッケージは183ファイルです。提出用ブックのオプションシート1万2千行も、全件照合して差がないことを確かめました。1つめの案件では、スクリプトが約15本になりました。保留だった項目の多くも、画面で確かめてOKにできました。

## 12. 確かめられないこと（6:00〜6:40）

このやり方で確かめられないこともあります。1つめの案件では、結果は文字で残し、画像は撮らなかったので、レイアウトや色の見え方は確かめられません。見られるのもテスト環境の画面だけなので、データベースの中身は直接は確かめられません。流すのは人なので、決まった時刻に無人で流すこともできません。流したのはテスト環境なので、本番だけで起きることは別に確かめる必要があります。画面や商品が変わったら、スクリプトの直しも要ります。

## 13. 似たサービスとの違い（6:40〜7:15）

最初に紹介したサービスと比べると、違いは4つあります。1つめは、仕様書とテストデータからAIで作ること。2つめは、お客様の環境に何も入れず、ログイン済みのブラウザに貼るだけで動くこと。3つめは、結果をお客様のチェックシートにそのまま書けることです。4つめは弱いところで、画面が変わったときの自動修復や、回帰テストを定期的に回す仕組みは、ツールのほうが整っています。

## 14. 考察（7:15〜7:35）

一度できたスクリプトは、貼り直せば同じ手順と判定基準で流せます。なので、速くなるのはスクリプトができた2回目からだと思います。前提の確認と、見た目で決めるところは人に残ります。

## 15. 横展開（7:35〜8:00）

同じ型が使えるかは、2つで見分けられると思います。同じ手順を何度も流すか、期待する結果を文字で書けるかです。リリースごとの回帰テストや帳票の検算は、実績に近い使い方です。直った不具合を、同じ手順で流し直して確かめるのにも使えます。移行後のデータ照合や、受注システムと基幹の突き合わせにも使えそうです。

## 16. まとめ（8:00〜8:10）

書くのはAIで、貼るのは人です。まずは、繰り返す仕事から試すのがよいと思います。

## 17. メッセージ（8:10〜8:20）

大事だったのは、自動化よりも、止まる・残す・照合する仕組みでした。ありがとうございました。
