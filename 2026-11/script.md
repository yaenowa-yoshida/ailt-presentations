# ブラウザのコンソールに貼るだけ　台本

2026年11月14日 CraftStage LT会（AIなんでもLightning Talk交流会）／富士通UIS（川崎）の台本です。スライドは[こちら](https://yaenowa-yoshida.github.io/ailt-presentations/2026-11/)です。

話す本文は約2,850字で、1分あたり約310字として約9分10秒です。料金は、スライドに書いた各社の公式サイト（2026-11-13確認）の参考値です。

## 1. タイトル（0:00〜0:15）

今日は**Claude Code** で作成したスクリプトを、ブラウザのコンソールに貼るだけの手順で、2つのサイトの**受け入れテスト**を回した話です。

## 2. 自己紹介（0:15〜0:35）

株式会社ヤエノワの吉田と申します。

普段はECサイトと他システムの連携の要件定義、設計、B2B発注システムと、アパレルのカスタムオーダーシミュレーターシステムの運用・保守を担当しています。

## 3. 自動テストとは（0:35〜1:05）

本題の前に、自動テストについて少しだけお話しします。テストには、ソフトウェアを動かさずに、レビューや静的解析で確かめる静的テストと、実際に動かして確かめる動的テストがあります。自動テストは、専用のツールでテストを自動で流し、実際の結果を期待結果と比べるものです。今日は、画面を動かして確かめるテストを、自動で流す話をします。

## 4. AIを使わないサービス（1:05〜1:40）

テストを作って動かす既存のサービスを紹介します。

AIを使わないものでは、サービスと言ってよいか分かりませんが、\
まずは**人力**があります。**人がテストシナリオを作って、人が目で見て手で実行するプロセスを踏みます。**\
次に**テスト自動化ツール**。人が画面の操作を記録して、ツールが何度でも流します。

参考までに、金額を1日あたりで比べると、外部に委託した場合は約3万2千〜18万円、ツールは月5千円くらいからです。

## 5. AIを使うサービス（1:40〜2:25）

最近では、ツールにAIが搭載されているサービスも増えています。

仕様書からテストケースを作るもの、例えば Autify Genesis（オーティファイ ジェネシス）や Katalon（カタロン）\
文章の指示でテストを作って流すもの、例えば MagicPod（マジックポッド）や QA Wolf（キューエーウルフ）\
画面が変わったときにテストを自動で直すもの、例えば mabl（メイブル）や BrowserStack（ブラウザスタック）があります。

設計書から合否判定、不具合の記録まで受け持つ、AGEST（アジェスト）の TFACT（ティファクト）のようなサービスも出てきています。料金は、1日あたりにすると約70円から2,700円くらいです。

## 6. 2つの案件（2:25〜3:05）

1つめは、B2B発注システムの改修で、81テストケースです。\
通常であれば人力で、テストケースを作成し、画面からの操作だけで対象データを選びます。テスト対象の商品を画面から選んで修正箇所を確かめ、発注できるかも確かめ、既存機能の回帰テストもします。

2つめは、ユニフォームのカスタム注文サイトの新商品で、90〜100品番。\
テストの項目は、1品番あたり約270手順あります。パーツごとに柄や色を選んだり、ON/OFFができるかを確かめたりと、バリエーションが多いためです。

通常であればこちらも人力で、デザインのバリエーション選択、数量・サイズ選択、注文確定、店舗側の注文受付と確定、工場向けのデータ作成までを、全品番で通して確かめる仕事です。

どちらも、サイトを開いているのは私のブラウザです。

## 7. 仕組み（3:05〜3:30）

そこで、Claude Code がテスト実施用のスクリプトを書き、私がブラウザのコンソールに貼ってテストを流します。

その結果を JSONで吐き出し、Claude Code が読んで判定し、OK／NGをチェックシートへ記録。NGの場合は内容と期待値、実際の結果、考えられる原因、ほかのバリエーションでの再現性を記録します。\
結果は文字でエクセルやスプレッドシートへ残し、開発チームと共有します。

流すのを人にしたのは、ほかのサードパーティのツールは、導入するまでのプロセスが難しいからです。

## 8. 手順（3:30〜4:25）

手順はこうです。まず、AIでテスト仕様書をつくりますが、基本的には自分でプロンプトに打ち込んでテストシナリオを作りました。

次に、商品とそれに付随するデータをダウンロードして、テストデータもAIで選定します。\
そのうえで、シナリオに合わせて Claude Code がスクリプトを書き、それを私がブラウザで実行します。

実行結果はJSONのログに残るので、Claude Code が結果を検証して、チェックシートにOKとNG、指摘点を記入します。

人がやるのは、最初にシナリオを打ち込むことと、ブラウザで流すことです。

1つめの案件では、1本のスクリプトをコピーして、別の確認用に作り替えていきました。

## 9. エージェントの紹介（4:25〜5:05）

両方の案件で働いてくれた、4つのエージェントを紹介します。

- 実行計画係\
  次にどのスクリプトを、どのアカウントと設定で流すかを決めて、進み具合も教えてくれます。読むだけで、何も書き換えません。
- スクリプト作成係\
  決まりを守ってスクリプトを書きますが、流しはしません。
- 結果記録係\
  結果を判定してシートに記録します。ただし書き込むのは、私が「書き込んでよい」と言ったときだけです。
- 仕様調査係\
  仕様書や経緯の記録を調べて、根拠つきで返してくれます。

## 10. 止まる仕組み（5:05〜5:45）

工夫の一つは、想定と違えば止まってそこまでのログを吐き出すことです。

どちらの案件でも、開始前に実行環境が合っているか、カートが空か、アカウントが想定どおりかを確かめ、何か一つが違えば実行しません。

実行中も、想定外のエラーが出たときや、期待どおりのボタンが無いときは、その場の画面の情報を取って止まります。次にチャット上で何を押せばよいかを私と会話の中で確認し、想定通りの動きになるようにスクリプトを直していきます。

こうした作りは、画面のスリープを止めるといったものと合わせて、7つの型にまとめました。

7つの型のうち、3つを紹介します。1つめは、実行中のスクリプト名と進み具合を画面の上に出すこと。2つめは、Wake Lock（ウェイクロック）で、実行中に画面をスリープさせないこと。3つめは、結果を文字で残すことです。画像は撮りません。

どちらの案件でも、金額をその場で計算して違えば止まり、注文番号がずれたら押さずに止まります。流し終えた注文は「済み」と記録して、二度流さないようにしました。

## 11. 残す仕組み（5:45〜6:15）

もう一つは、決めたことを次の会話に残すことです。1つめの案件では、作業のルールを CLAUDE.md に書き、決めたことや訂正はメモリに残して、約35件になりました。2つめの案件では、OKにした根拠を備考に書き、途中から伝えた「いちいち確認しなくていい」も、メモリに残しました。

## 12. 成果（6:15〜6:55）

どちらの案件でも、回帰テストと、決まった内容を再現する作業の時間が、圧倒的に短くなりました。2つめの案件では、手作業だと1件10分以上かかる注文が約30秒になり、33件を通して回しました。工場向けの送付パッケージは183ファイルです。提出用ブックのオプションシート1万2千行も、全件照合して差がないことを確かめました。1つめの案件では、スクリプトが約15本になりました。保留だった項目の多くも、画面で確かめてOKにできました。

## 13. 確かめられないこと（6:55〜7:35）

このやり方で確かめられないこともあります。1つめの案件では、結果は文字で残し、画像は撮らなかったので、レイアウトや色の見え方は確かめられません。見られるのもテスト環境の画面だけなので、データベースの中身は直接は確かめられません。流すのは人なので、決まった時刻に無人で流すこともできません。流したのはテスト環境なので、本番だけで起きることは別に確かめる必要があります。画面や商品が変わったら、スクリプトの直しも要ります。

## 14. 似たサービスとの違い（7:35〜8:10）

最初に紹介したサービスと比べると、違いは4つあります。1つめは、仕様書とテストデータもAIで作ることです。大量のデータを目で見てテストデータを選ぶのは、本当に大変です。AIに判断してもらうと、組み合わせや網羅性、仕様の漏れも見ながら選べるので、テストデータの選定がものすごく楽になりました。2つめは、お客様の環境に何も入れず、ログイン済みのブラウザに貼るだけで動くこと。3つめは、結果をお客様のチェックシートにそのまま書けることです。4つめは弱いところで、画面が変わったときの自動修復や、回帰テストを定期的に回す仕組みは、ツールのほうが整っています。

また、今回求められたことを、1つのサービスですべてまかなうことはできず、いくつかのサービスを組み合わせる必要があります。

まとめると、このやり方は柔軟に作れて、お客様の環境に何も足さずに始められます。ただ、ログイン済みのブラウザで動かすので、貼るスクリプトの中身は確かめる必要がありますし、仕様書やデータをAIに渡してよいかも、お客様と確かめておく必要があります。

## 15. 考察（8:10〜8:25）

一度できたスクリプトは、貼り直せば同じ手順と判定基準で流せます。回帰テストも段違いに速く、楽に流せます。結果を文字で残しているので、前回の実施との差も見分けられます。なので、速くなるのはスクリプトができた2回目からだと思います。前提の確認と、見た目で決めるところは人に残ります。

## 16. 横展開（8:25〜8:55）

同じ型が使えるかは、2つで見分けられると思います。同じ手順を何度も流すか、期待する結果を文字で書けるかです。リリースごとの回帰テストや帳票の検算は、実績に近い使い方です。直った不具合を、同じ手順で流し直して確かめるのにも使えます。移行後のデータ照合や、受注システムと基幹の突き合わせにも使えそうです。

## 17. まとめ（8:55〜9:05）

書くのはAIで、貼るのは人です。まずは、繰り返す仕事から試すのがよいと思います。
