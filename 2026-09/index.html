Built

ファンとの関係ごとに、4つのシステム

目的は「自分を知ってる人にも、知らない人にも、新曲と活動をリーチする」

相手システムねらい構成
新規層休日生態系診断興味を持ってもらう入口Workers（完全静的）
購入を迷ってる層10時間配信システム購入の後押し、拡散のきっかけWorkers・KV＋ローカルNode.js
イベント参加者アンケート＆ボイス配布満足度向上、品質改善Workers・D1・R2・KV・Turnstile
既存ファン全イベント参加特典の動画配信継続参加への感謝Workers・R2

4つは別々のアプリ。アンケートは回答を保存するのでDBとボット対策を足し、特典動画は大きなファイルを配るのでストレージだけ。用途ごとに必要な構成だけを選んでいる

出典: Cloudflare登壇、Qiita「現役アイドルに学ぶ、AI駆動開発のはじめ方」（tomy0610）

Flow

ものづくりのフローは7段階、PCは2回だけ

登壇で示された流れ。設計は「1日以内に終える」のが目標（実際は3日）

1 着想スマホ
2 安全確認スマホ
3 仕様書化スマホ
4 試作PC
5 テストスマホ
6 修正PC
7 公開・運用スマホ
  • 着想：スマホでAIに相談。「最小限に絞るなら何を残すか」「個人開発の規模で実現できるか」
  • 安全確認：「この仕組みで悲しむ人はいないか」を洗い出す。開発者側（コスト・復旧・両立）とユーザー側（環境・分かりやすさ・期待）
  • 仕様書化：「どう動けば成功か」を書く。当日の運用と、問題が起きた時の対応までMarkdownに
  • スキマ時間の積み上げで、全体3〜4時間ほど（登壇での整理）

出典: Cloudflare Workers Tech Talks in Tokyo #8 での本人の登壇（2026-08-27）、本人ブログ（2026-08-01）

The Four

「悲しむ人を生まない」ための4つの守り

登壇で本人が挙げた4つ

守り ①

時短

スマホで完結。移動中でも対応できる状態を作る。Markdownのフォーマットに落として再利用する

守り ②

セキュリティ

個人情報を預からない。複数のAIにレビューさせる。壊れても笑って済ませられるものしか作らない。本番運用まで想像して設計する

守り ③

無料枠を最大活用

コストも機能要件。無料枠か低コスト枠で成立するか。クレカ登録なしで試せるか。上限に近づいたらアラート

守り ④

サービスへの想い

既存の競合施策を下調べする。絶対に損ないたくない体験を明確にする。ファンへのメッセージはAIに書かせず自分の言葉で

出典: Cloudflare Workers Tech Talks in Tokyo #8 での本人の登壇（2026-08-27）、本人ブログ（2026-08-01）

The Four 1/4 · Time

「時短」＋「誰かの悲しみを想像する」

多忙な本業と両立するための設計。これも要件

時短＝運用できる範囲に絞る

・着想〜仕様書はスマホ。PCは試作と修正だけ
・設計は1日以内が目標。時間をかけると「何がしたかったか」がぼやける
・配信中はスマホの管理画面から数字もテロップも直せる。アンケートは当日スマホで声を録音してアップ、QRをその場で発行、イベント日を過ぎたら締切
・ツアーで移動しながら回せる範囲でしか作らない

安全確認＝2つの悲しみ

開発者側：高コストになってないか、トラブル時に自分で復旧できるか、本業と両立できるか

ユーザー側：特定の端末でしか見られなくないか、受け取り方が分かりにくくないか、期待させた体験を本当に届けられるか

出典: Cloudflare Workers Tech Talks in Tokyo #8 での本人の登壇（2026-08-27）、本人ブログ（2026-08-01）

The Four 2/4 · Security

「壊れても笑えるものだけ作る」

セキュリティを「作らない判断」から始めてる

本人が決めたこと

・個人情報はなるべく預からない（診断サイトは個別診断するが個人情報を持たない）
・アンケートのデータは一定期間で削除か匿名化
・Turnstileでボット対策、書き込みAPIは全部トークン保護
・複数のAIに製品をレビューさせる

同じ週のニュース

預かった情報を守れなかった話

RIZAP、社員が個人利用の生成AIに氏名・疾患情報を誤アップロード。IHI健保分は210人（Ledge.ai 2026/9/8）

企業の側が「預かった情報を守れなかった」話をしてる横で、本人は「預からない」から始めてる。

預からなければ漏れない。壊れても笑えるものなら止まっても困らない。守りの一番上流は「何を持たないか」

出典: Cloudflare Workers Tech Talks in Tokyo #8 での本人の登壇（2026-08-27）、本人ブログ（2026-08-01）

The Four 3/4 · Cost

「コストも機能要件」

無料枠で成立するかを、設計の条件に入れてる

無料枠で組んだ構成

診断サイトは .workers.dev のまま完全静的で無料。特典動画は R2 の月10GB無料枠とエグレス無料。X検索は RapidAPI 月1ドル・1,000リクエスト上限で超過課金なし

制約は設計を変える理由

Cron が Workers 無料プランで使えない → 自動ポーリングを捨てて手動ボタンに。「盛り上がりに合わせて取得間隔を制御できて、運用はむしろ良くなった」

本人の言葉

従量課金に不安があった。Cloudflareはクレカ登録なしで試せるサービスがあり、心理的ハードルが低かった。「AI開発を応援してもらえているような気がした」

AIのAPIはモデルごとにトークン単価が決まっていて、従量課金で使うほど請求が伸びる。新しいモデルが出るたびに単価も変わる夏に、「上限のある枠で成立させる」を先に決めてる

出典: Cloudflare Workers Tech Talks in Tokyo #8 での本人の登壇（2026-08-27）、本人ブログ（2026-08-01）

The Four 4/4 · Message

「メッセージは、AIに書かせない」

何をAIに任せて、何を任せないかを先に決めてる

本人が線を引いたところ

・実装：全部AI。コードは1行も読まない
・仕様書：AIと壁打ちしながら自分で書く
・ファンへのメッセージ、ボイス、企画：自分の言葉、自分の声
・既存の競合施策を下調べしてから作る（ファンの気持ちで）

同じ週のニュース

AI生成文書をAIで要約する「doom loop」

Microsoft Office責任者が、AI生成文書をAIで要約する職場の流れを「doom loop」と指摘（Ledge.ai 2026/9/8）。AIスロップ＝AIで量産された中身の薄いコンテンツ（slopは残飯の意）。職場では、AIで書いた文書を相手がAIで要約し、誰も読まない文書が増え続ける状態。出るのは、任せる範囲を決めずに全部投げるから。

「絶対に損ないたくない体験」を先に決めると、AIに投げていい範囲が決まる。順番が逆だとスロップになる

出典: Cloudflare Workers Tech Talks in Tokyo #8 での本人の登壇（2026-08-27）、本人ブログ（2026-08-01）

Requirements

機能要件と非機能要件に分けると

彼女の言葉を、僕の仕事の言葉に置き換える

笑顔にする

機能要件

・CD購入と応援投稿でゲージが伸びる
・閾値を超えたら「衣装 解禁！」の演出
・AIがMVの再現度を採点して画面に出す
・アンケートに答えたらその日だけのボイスが届く
・全イベント参加でコンプリート動画

悲しむ人を生まない

非機能要件

① 時短 → 運用性。誰が・どの端末で・何分で対応するか
② セキュリティ → 情報の保持方針。何を持たないか。持つなら期限と削除
③ 無料枠 → コスト上限。予算を要件に入れる。超えたら検知して止める
④ 想い → 体験の品質。損なってはいけないものを先に固定する

Summary

まとめ

01

ファンとの関係ごとに4つのシステム

診断は静的ファイルだけ、アンケートはDBとボット対策、特典動画はストレージだけ。用途ごとに独立させ、必要な構成だけ選んだ

02

着想、安全確認、仕様書化をスマホで

「この仕組みで悲しむ人はいないか」を、仕様書より前に確認した

03

4つの守り

個人情報を預からない／無料枠で成立させる／ファンへのメッセージはAIに書かせない／スマホで回せる範囲で作る

04

笑顔にする側が機能要件、悲しむ人を生まない側が非機能要件

笑顔にする側はゲージ・解禁演出・AI採点・ボイス。どちらも先に決めてから、AIに実装を投げた
